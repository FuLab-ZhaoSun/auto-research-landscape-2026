# 整合方案：从这批项目里取什么、怎么拼

> 目标不是「把 70 个项目拼成一个系统」，而是判断哪些机制可以组合、组合后在哪里放大、在哪里失效。
> 技术路线划分见 [技术路线归类](tech-routes.md)，本文只讨论「提取精华 + 组合」。

## 先给结论

1. **可以整合，但不是全部**。8 条路线里，工具层、状态层、编排层、搜索层、评测层、产物层是**分层互补**关系，存在清晰的接口边界；领域工具与领域评测**不可跨域复用**，多智能体角色层**证据最弱**。
2. **整合的真实收益是三项**：可靠性（可审计、可回滚、可复现）、覆盖度（动作空间）、搜索效率（状态 + 搜索）。它**不产生**「自动创新」。
3. **整合的硬边界是评测**：没有自动 evaluator 的领域，拼再多层也只是流程更漂亮；有 evaluator 的领域（方程发现、符号回归、MLE、材料计算）才是整合能兑现价值的地方。
4. **建议只 vendor 4 个核心模块**：研究状态、搜索运行时、工具注册、评测闸门；其余全部用适配器，避免 10 个依赖面同时腐烂。

## 一、精华提纯：每条路线最值得拿的机制

| 路线 | 值得拿的精华 | 出处 | 丢掉什么 |
|---|---|---|---|
| 编排 | 外层只做流程，执行交给通用编码 agent；**环境工程优先于提示词** | AI-Scientist-v3、EurekAgent | 固定模板流水线（The AI Scientist、AutoResearchClaw 的早期形态） |
| 编排 | **确定性护栏**核对引用/数字/结论，防 rubric reward hacking | ScholarLoop | 纯靠模型自述的「自我检查」 |
| 编排 | 并行实验树 + 预算上限 + HITL 检查点 | AI-Scientist-v3（并行实验树）、AutoResearchClaw（HITL）、PRAXIST（并行 peer + 代际综合） | 无限轮次的「自主」 |
| 状态 | **假设树 + 证据剪枝**：子假设作为节点，证据决定去留 | Arbor | 用对话历史当记忆 |
| 状态 | **调查状态与主张裁定分离**，防过度解读 | StatefulDiscovery | 让模型直接宣布「结论成立」 |
| 状态 | **科研资产图**：数据/知识/工具/技能带依赖关系，可演化 | MatOS | 万能 schema（见风险 3） |
| 搜索 | LLM 作变异算子 + **样本效率**优先 | ShinkaEvolve、OpenEvolve | 无评测函数的「进化」 |
| 搜索 | **搜索运行时**：候选持久化、复杂度、Pareto、可回溯 | SRHarness | 把搜索逻辑写死在提示词里 |
| 搜索 | **多 worktree 并行种群 + 多父代选择**，避免单上下文收敛 | SwarmResearch | 单线程长时间搜索 |
| 工具 | **动作空间发现**：从文献挖工具、数据库、协议，自动构建可调用环境 | Biomni | 手工枚举工具清单 |
| 工具 | 统一 MCP 注册 + 能力清单（schema、成本、权限） | ToolUniverse | 跨域「通用工具层」（见「不该做」） |
| 工具 | **逐工具校准**：每个工具单独验证输出分布，而不是假设都可靠 | Chorus | 把工具当黑盒 |
| 角色 | generate → critique → evolve → rank 的**对抗式筛选** | Google Co-Scientist | 常驻多角色（无外部信号时会互相附和） |
| 角色 | 明确分工（Planner/Coder/Controller/Interpreter） | NS-Copilot、STAT | 为了「多 agent」而多 agent |
| 物理 | **干湿闭环**：ML 设计 + 机器人执行 + 真实测量反馈 | PRAXIS | in-silico 冒充实验证据 |
| 物理 | 湿实验基准的**提交/挂起续跑**框架 | AISLE | 只评代码产出 |
| 产物 | **论文 → 可交互 agent**，把代码/数据/工作流变成可执行引用 | Paper2Agent | 只生成 PDF |
| 产物 | **技能链**：想法→文献→实验→写作，每环可替换、可单独评测 | Spark-to-Paper | 单体端到端黑箱 |
| 产物 | 可编辑产物（SVG/PPTX）+ 对象级可编辑性指标 | DrawAI、PaperBanana | 只追求「看起来像」 |
| 产物 | **引用断言核查**：文献是否存在、是否真的支撑该 claim | RefWarden | 只查引用格式 |
| 评测 | 真实数据 + 真实 SOTA（不是 toy benchmark） | NatureBench、BAISBench | 自造数据集自评 |
| 评测 | 开放题 + 专家预设条件，接受「多数失败」的结果 | Into the Unknown | 只报成功率 |
| 评测 | **运行时完整性干预**：数据泄漏/指标误用/事后挑选检测 | RIDAR | 只在跑完后看指标 |

## 二、整合架构：六层 + 两个横切

```text
┌─────────────────────────────────────────────────────────────┐
│ L6 产物与传播   论文/图表/论文→agent/引用核查                │
├─────────────────────────────────────────────────────────────┤
│ L5 评测与审计   领域 evaluator + 隔离协议 + 完整性报告        │
├─────────────────────────────────────────────────────────────┤
│ L4 搜索与选择   进化/种群/树搜索 + 预算调度                   │
├─────────────────────────────────────────────────────────────┤
│ L3 编排与执行   任务图 harness：调用编码 agent、并行分支      │
├─────────────────────────────────────────────────────────────┤
│ L2 研究状态     假设树 + 证据 + 产物 lineage + claim ledger   │
├─────────────────────────────────────────────────────────────┤
│ L1 工具与动作空间  MCP 注册 + 能力清单 + 逐工具校准            │
├─────────────────────────────────────────────────────────────┤
│ L0 基础设施     沙箱/预算/审计日志/可回放                     │
└─────────────────────────────────────────────────────────────┘
   横切：HITL 检查点（选题、结论、投稿前） · 全链路 trace
```

### 层间契约（最小接口）

| 层 | 最小接口 | 关键约束 |
|---|---|---|
| L1 | `registry.list/search/invoke(tool, args)`；每个工具带 input schema、成本模型、权限标签、校准器 | 工具必须可单独测试；跨域工具不共用 |
| L2 | `state.apply(node/edge/artifact)`、`state.checkpoint/diff`、证据指针指向不可变产物 | 核心字段少（见下），域扩展放 sidecar |
| L3 | `harness.submit(task, budget, sandbox_profile) → run`；run 产出 artifacts + trace | 执行器可替换（Claude Code / Codex / 本地） |
| L4 | `search.propose(parent, state) → candidates`、`search.score` | 无 evaluator 时禁止启动搜索 |
| L5 | `gate.evaluate(artifacts, protocol) → metrics + integrity_report` | 协议版本化、数据隔离强制 |
| L6 | `artifact.render(kind)`、`artifact.verify(citations)` | 产物必须带 lineage 指针 |

### 状态核心 schema（只保留四个概念）

```json
{
  "question": "研究问题",
  "hypotheses": [
    {"id": "h1", "parent": null, "claim": "...", "status": "open|supported|refuted",
     "evidence": ["artifact:exp-001"], "decided_by": "gate:v3"}
  ],
  "artifacts": [
    {"id": "exp-001", "kind": "code|data|figure|paper|agent",
     "path": "...", "hash": "...", "lineage": ["h1", "exp-000"]}
  ],
  "claims": [
    {"id": "c1", "text": "...", "supported_by": ["artifact:paper-01"], "verified": false}
  ]
}
```

> 为什么只有四类：多出来的状态字段几乎都是某个领域/某个评测的副产品，塞进通用层会让 schema 变成瓶颈。

## 三、四个乘法点：为什么这样拼能放大

1. **状态 × 搜索**：搜索要能剪枝、回溯、避免重复实验，前提是状态可读可写。没有状态，进化搜索退化成随机重试；有了假设树，搜索可以只在「未决节点」上花预算。这是 1+1>2 最确定的一处。
2. **工具 × 编排**：长程任务的价值取决于动作空间大小。工具层决定 agent「能做什么」，编排层决定「做多久」；两层都成立时，端到端才有意义。
3. **评测 × 审计**：单一评测会被过拟合（PNAS 2026 的四类问题：基准选择、数据泄漏、指标误用、事后挑选）。确定性评测闸门 + 运行时完整性检查组合，才能把「分数」变成「可信分数」。
4. **产物 × 核查**：写作层接入引用断言核查后，「像论文」才变成「可追溯」；Paper2Agent 再把论文变成可执行引用，形成闭环。

## 四、风险：整合会在哪里失效

1. **成本是乘法，不是加法**：并行编码 agent × 进化轮数 × 多角色评审。必须有预算控制器（按任务分配 token/GPU/墙钟时间）：PRAXIST 的「任务自有评测 + 并行 peer」是一种把预算写进任务定义的思路，可以直接借鉴。
2. **评测缺口是硬边界**：没有自动 evaluator 的领域（多数实验科学），整合只能提高流程规范度，不能提高结论可信度。**先选有 evaluator 的域**，再谈整合。
3. **状态通用化陷阱**：想要一个 schema 装下所有领域，最后变成一个谁都不好用的中间层。核心四概念 + 领域 sidecar 是唯一可持续的折中。
4. **角色层证据最弱**：没有外部信号时，多 agent 容易互相附和，把错误放大。默认单 agent + critic gate，多角色只在「有独立评测信号」时开启。
5. **安全是前置条件**：会执行 LLM 生成的代码 + 调用 MCP 工具 + 提交 HPC 作业。沙箱、网络、预算、权限四件事必须先在 L0 解决，否则不要接真实环境。
6. **维护是 10 个依赖面**：70 个项目里只 vendor 4 个核心模块，其余用适配器；否则半年后连环境都装不起来。
7. **整合不产生 novelty**：选题、问题定义、结论是否算「新」，仍由人判断。Denario 在论文里明确把 novelty assessment 留给用户检查，这个设计值得照抄。

## 五、MVP：四个阶段，每阶段有验收闸门

> 前提：先选一个**已有自动 evaluator** 的域。推荐顺序：方程发现/符号回归（SRHarness、SR-Scientist 有成熟评测）→ MLE 任务（MLE-bench）→ 材料计算（MatOS 类工具）。

| 阶段 | 内容 | 验收闸门（硬指标） |
|---|---|---|
| P0 | 选域 + 沙箱/日志/预算骨架 + 复现一个基线 | 基线在标准评测上复现成功，trace 完整可回放 |
| P1 | L2 研究状态（假设树）+ L3 harness | 重复实验率下降 ≥50%；失败可归因（能定位到假设/工具/评测哪一层） |
| P2 | L4 进化搜索运行时 + L1 MCP 工具注册 | 固定预算下达到或超过基线的最优结果；搜索过程可复现 |
| P3 | L5 确定性评测闸门 + 完整性检查 | 审计报告完整（数据隔离、指标版本、选择偏差检查全过） |
| P4（可选） | L6 产物链 + 人机检查点 | 产物带完整 lineage；关键 claim 经引用核查 |

**不要用「论文得分」当验收指标**——那正是最容易被 gaming 的地方。用成本/结果、可复现率、失败归因覆盖率、审计通过率。

## 六、组件选型建议（vendor / adapt / reimplement）

| 层 | 借鉴来源 | 建议方式 | 理由 |
|---|---|---|---|
| L0 沙箱与预算 | 无单一来源 | 自建 | 安全是底座，必须自己可控 |
| L1 工具注册 | ToolUniverse | adapt | MCP 生态已成熟，直接接 |
| L1 动作空间发现 | Biomni | adapt（仅新领域冷启动时用） | 一次性建设成本高，适合领域扩展 |
| L1 工具校准 | Chorus | reimplement（思路） | 逐工具校准是低成本高收益 |
| L2 研究状态 | Arbor + MatOS | reimplement（核心四概念） | 直接 vendor 会和域耦合 |
| L3 编排 | AI-Scientist-v3 + EurekAgent | adapt | 编码 agent 编排是当前最稳执行层 |
| L3 护栏 | ScholarLoop | reimplement（确定性检查） | 成本低、直接降低 reward hacking |
| L4 搜索运行时 | SRHarness | vendor | 候选/Pareto/持久化是通用能力 |
| L4 变异算子 | ShinkaEvolve | adapt | 样本效率策略可复用 |
| L5 领域评测 | NatureBench / BAISBench / MLE-bench | adapt（按域选一） | 评测不能跨域复用 |
| L5 完整性审计 | RIDAR | reimplement（规则） | 规则可移植，实现需适配 |
| L6 引用核查 | RefWarden | vendor | 独立能力，接口清晰 |
| L6 论文→agent | Paper2Agent | adapt | 对内部知识库价值高，优先级低 |
| HITL | AutoResearchClaw / PRAXIST | reimplement | 检查点设计因组织而异 |

## 七、不要做的事

1. **不要一开始做跨域通用工具层**——先把一个域的工具做扎实。
2. **不要把 70 个项目都接进来**——选 6–8 个核心，其余只借鉴思路。
3. **不要用多 agent 角色替代评测**——角色不会告诉你结论对不对。
4. **不要在无 evaluator 的领域做端到端全自动**——那只会更快地产生不可信结论。
5. **不要把论文写作放进 MVP**——它是最后一公里，不是核心能力。
6. **不要相信「自主」**——选题与结论价值必须有人类检查点。

## 八、一句话判断

**这套项目集合最适合整合成一个「有状态的、可审计的、在强评测领域里做搜索的研究 harness」，而不是一个「什么都能做的通用 AI 科学家」。**
前者的边界清晰、收益可验证；后者会把所有路线的弱点叠加在一起。
